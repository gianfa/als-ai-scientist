# Observer UI

A local, read-only web UI over the runs under `experiments/`: the runs of the phase pipeline, and the archived `e2e-*` runs of the previous architecture. It is for inspection only: it changes nothing and has no authentication, so keep it on `127.0.0.1`.

Start it on its own (the previous launcher started it automatically; `run.sh` no longer does):

```bash
scripts/ops/launch-observer-ui.sh [--host HOST] [--port PORT]     # default http://127.0.0.1:8765/
```

## Menu and run selector

The menu has one item:

- **Run** shows one run. The run is chosen once, in the selector at the top, and every view below reads that same run. The newest run is selected by default. A **run in progress** button appears when a run is live and jumps to it; a pipeline run is live while the orchestrator recorded in its `run.pid` is alive. Under the selector, a **Stages** strip shows each phase the run was launched with: passed, running, not started, or failed where an ended run stopped (the archive does not tell a failure from a manual stop). An archived `e2e-*` run shows its old stages instead.

Addresses are linkable and survive a reload: `#run/<run-id>`, `#run/<run-id>/<view>` with `<view>` one of `overview`, `graph`, `flow`, `agents`, `story`, `tokens`, `evaluation`; `#run/<run-id>/agents/<phase>` opens Agents scrolled to that phase, which is where each agent's stage links in Story lead.

### Story

- **What happened** is generated by fixed templates from the recorded journals: evidence items returned and checked, the causal graph built, hypotheses proposed, critic verdicts, revisions, and how the run ended. A step with no recorded data produces no sentence, and no model writes the text.
- **Agent conversation** shows, in prompt order, the workflow's prompt to each agent (left) and the agent's reply (right). Critic replies carry a verdict label (`rejected`, `revise`, `surviving`).
- Between messages, neutral **events** say what the workflow did with a reply, for example `Revision H3 rejected` (expand for the reason), `8 evidence records dropped`, and a closing `Run ended: ...` with the outcome. They come from the workflow's own log lines; an unrecognised line is shown verbatim.

Limits worth knowing:

- Agents do not message each other in this workflow: the workflow script prompts each agent and receives its reply, so every exchange is workflow -> agent.
- Prompts are timestamped (`prompts.jsonl`); replies and workflow events are not, so they show "time not recorded" and are placed after the agent they belong to, not at an exact time.
- Prompt and reply text is cut at 6000 characters in the UI and marked `(truncated)`; the full text is in `prompts.jsonl` and the journals.
- A phase-pipeline run has no `prompts.jsonl`: its conversation is read from `NN-<phase>-journal.jsonl`, and **What happened** is one line per phase report (agents started and answered, workflow status, CLI-reported cost, tokens, wall time). Agents of the phase pipeline do not talk to each other either: each phase workflow gives each agent one prompt and keeps its one structured result (`agent(prompt(item), ...)` in `workflows/phases/src/*.js`), and agents share what they learn only through the knowledge base. So each exchange shows, between prompt and result, the agent's own **tool calls** in order (`NN-<phase>-agent-tools.jsonl`, inputs cut at 300 and results at 200 characters by the extractor), `kb_*` reads included. The prompt and its time appear only when the run archived its agents' transcripts (`transcripts/<stage>/`, from `pl-prod-013` on); otherwise the prompt is marked not archived.
- The run selector's cost and tokens for a phase-pipeline run are the sums over its phase reports, plus the cost of earlier failed attempts (`<stage>-result.json`); a replay archive counts only the phase it re-ran.
- A run without `prompts.jsonl` and journals (store and smoke runs) shows an empty-state message.
- A run that ends with `insufficient evidence` is a valid outcome, not an error: the closing event says why.

## Endpoints

The server is read-only JSON over HTTP; the list is in the docstring of `observability/wf_observer/server.py`. Run-scoped endpoints (`/runs/<id>`, `/events`, `/story`, `/stages`, `/metrics`, `/phases`, `/roles`, `/tokens/<id>`, `/evaluation/<id>`) all resolve the run through one catalog, so an id offered by the selector works in every view.
